# Service Rewards

Hashgram pays for useful work: storing bytes that were assigned and proven,
relaying and serving bytes that clients signed for, and carrying calls.
Nothing is paid for a declared disk, a running process, or a node's own
counters. This document is the operator's and auditor's guide to how
evidence is produced off chain and settled on chain.

## Roles and evidence

| Chain role | Node roles | Evidence | Paid on |
| --- | --- | --- | --- |
| `STORAGE` | `store` | on-chain `StorageAssignment` + answered `StorageChallenge`s | bytes held across an epoch × challenge pass rate |
| `RELAY` | `relay`, `bootstrap`, (`store` for mailbox delivery) | client-signed `ServiceReceipt`, role RELAY | bytes |
| `MEDIA` | `media`, `store` | client-signed `ServiceReceipt`, role MEDIA | bytes |
| `CALL` | `call` | client-signed `ServiceReceipt`, role CALL | seconds |

Credit is proportional and exact: `bytes × rate × 10⁶ / GiB` (and
`seconds × rate × 10⁶ / 3600` for calls), so a kilobyte of real service is
a positive integer. Credit is only ever compared with other credit — a
provider's payout is its share of an epoch's budget — so the scale is a
choice, and it was chosen so small clients count. (An earlier version
truncated units to whole gibibytes before multiplying, which made relay
rewards unreachable for messaging; the `phase2.sh` acceptance now asserts
positive credit from real client receipts.)

## Keys, and what each can do

| Key | Where | Purpose | If stolen |
| --- | --- | --- | --- |
| node key | `/var/lib/hashgram/node/node_key` | peer identity; signs announcements and challenge answers | attacker impersonates this node's peer id and can answer challenges *if it also has the bytes* |
| operator key | `/var/lib/hashgram/node/operator.key` | registers the provider, submits receipts, answers challenges, assigns storage | attacker can begin unbonding (delayed), submit forged receipts (which the chain scores as fraud), and move the operator account's balance |
| reward address | anywhere else | receives payouts | nothing on this machine |

The operator key is hot because it must sign challenge answers unattended.
It is generated by `hashgram-node operator-key` as the node's own service
account (`hashgramctl configure-role` does this for earning roles) and holds
only the bond plus fees. The reward address should be a cold key.
`mainnet-preflight` fails if either key file is readable by anyone else.

## Registration

```text
hashgramctl configure-role relay,store --declared-storage 500000000000 --reward-address hash1cold...
   → prints the operator address
fund the operator address with ≥ 1,000 HASH (the bond) + fees
set auto_register_provider = true in /etc/hashgram/node.toml; hashgramctl restart
```

On start the node checks `/hashgram/serviceproof/v1/provider/<operator>`
and, if absent and configured to, sends `MsgRegisterProvider` with its
node public key (ed25519), the chain roles mapped from its node roles, the
bond, declared storage and moniker. `hashgramctl rewards` and
`hashgramctl status` show the result.

## Storage

1. **Assignment.** Only registered assigners may call `MsgAssignStorage`
   (`assigners` in genesis, changeable by governance). A node whose operator
   is an assigner records an assignment for each complete blob it holds
   (replica 0) and for each replica it pushed to a known provider, with the
   blob's size, chunk count and SHA-256 Merkle root (leaf prefix `0x00`,
   node prefix `0x01`, odd node paired with itself). Assignments cannot
   exceed the provider's declared storage.
2. **Challenge.** At each epoch the chain picks, per provider,
   `challenges_per_epoch` (default 4) random `(assignment, chunk)` pairs from
   the previous app hash and issues `StorageChallenge`s with a deadline of
   `challenge_response_blocks`.
3. **Answer.** The node polls `/hashgram/serviceproof/v1/challenges/<operator>`
   every minute, reads the chunk from its store, computes the leaf hash and
   Merkle path, signs `CanonicalChallengeResponseBytes` with its node key
   under `storage-challenge`, and sends `MsgAnswerChallenge`. The Rust
   implementation is byte-identical to Go and pinned by vectors in
   `hashgram-proto::merkle`.
4. **Credit.** Bytes held for the whole epoch earn
   `bytes × storage_credit_per_gib_epoch × 10⁶ / GiB × passed / issued`.
   A missed challenge is a failure; repeated failures raise the fraud score
   and jail the provider.

The assigner set is a centralisation point and is documented as such in
`docs/DECENTRALIZATION.md`. Mainnet genesis ships it **empty**: nothing can
earn storage credit until governance registers the first assigner.
`hashgramctl propose add-assigner <operator-address>` writes the proposal
file with the live parameters and one address added (a parameter update
replaces the whole set, so never write this file by hand); submit and vote
with `hashgramd tx gov`. Adding community assigners later is the same
proposal.
An assigner can assign its own blobs to itself; the challenge still requires
holding the bytes, and the concentration cap below bounds what any one
provider can take from an epoch.

## Receipts

A client that was served signs:

```protobuf
message ServiceReceipt {
  string provider = 1;      // operator address, from the handshake
  int32  role = 2;          // RELAY 2, CALL 3, MEDIA 4
  bytes  client_pubkey = 3; int32 client_key_type = 4;   // ed25519 device key
  uint64 epoch = 5;         // the open epoch
  uint64 nonce = 6;         // unique per (provider, client)
  uint64 units = 7;         // bytes or seconds
  int64  expiry_height = 8;
  bytes  client_signature = 9;
}
```

The SDK signs a `MEDIA` receipt after every verified download and a `RELAY`
receipt after every mailbox fetch that delivered bytes, and hands it to the
provider over `/hashgram/rpc/1` (`ReceiptDeliver`). The client is never
blocked by this; a receipt is the provider's reward.

The node checks the receipt names itself, the role is one it offers, the
signature verifies, the epoch is open, the nonce is new, and the client is
not its own key; then it batches up to 100 and submits `MsgSubmitReceipts`
once a minute. The chain re-checks everything, refuses self-traffic
(client = operator, reward address or node key), replays and oversized
units with fraud scores, and credits proportionally. Credit from any one
client is discounted above `max_client_concentration_bps` (20%) of the
provider's total, which is what makes two nodes trading fake traffic
unprofitable.

## Settlement

Epochs are `epoch_blocks` long (default 21,600 ≈ 24 h). At an epoch close
the chain computes each provider's effective credit, caps any provider at
`max_provider_share_bps` (5%) of the epoch budget, and pays from the
useful-service reserve (500,000,000 HASH at genesis, released on a
decreasing schedule; `docs/TOKENOMICS.md`). `hashgramctl rewards` shows the
open epoch's credit, the effective credit after discounts, and lifetime
payouts; `/hashgram/serviceproof/v1/rewards/<operator>` is the raw query.

## Operator checklist

```text
hashgramctl rewards                       agent stats, pending receipts, epoch credit, payouts
hashgramctl storage                       blob counts, degraded blobs, assignments, open challenges
journalctl -u hashgram-node | grep -E 'challenge|receipt|assignment'
curl 127.0.0.1:26672/v1/rewards           the agent's own view
```

A node that earns nothing usually has one of: no operator key, an unfunded
operator, `auto_register_provider = false`, no assigner recording its
storage, or clients not reaching it (no receipts). `hashgramctl rewards`
names which.

## Known limitations

- Challenges prove a node can produce assigned chunks; they do not prove
  that three replicas are on three different machines. Replication is
  reported honestly (`DEGRADED`) but not proven on chain.
- Call receipts are not produced by the reference client.
- Receipt submission costs the provider gas; a provider serving only tiny
  clients pays fees to claim small credit. Batching to 100 per transaction
  bounds this.
